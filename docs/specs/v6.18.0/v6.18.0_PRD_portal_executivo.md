# PRD — v6.18.0 · Portal do Cliente, primeiro recorte (Portal Executivo)

> **Status**: especificação, não implementado. Nenhum código, schema, frontend ou backend foi alterado na elaboração deste documento.
> **Módulo novo**: Portal do Cliente — primeira funcionalidade da plataforma desenhada primariamente para o executivo da empresa cliente, não para o analista da GD Conecta.
> Base: plataforma v6.17.0 (última versão lançada, `11_changelog.md`). Alinhado a `00_contexto_oficial.md` §9 (atualizada 2026-08-06) e `22_plano_diretor_tecnico.md` §16 (atualizada 2026-08-06).
> Companion: [`v6.18.0_validacao_estrategica.md`](v6.18.0_validacao_estrategica.md) (aprovação estratégica) e [`v6.18.0_prototipo_funcional_portal_executivo.md`](v6.18.0_prototipo_funcional_portal_executivo.md) (protótipo navegável).
> **Este PRD não define arquitetura, endpoint, schema ou migration** — essas decisões pertencem à Especificação Técnica, etapa seguinte do processo oficial (`22_plano_diretor_tecnico.md` §17), ainda não iniciada.

---

## 1. Visão geral da funcionalidade

Um app novo, separado da aplicação interna que o analista usa hoje, com autenticação própria, onde um executivo da empresa cliente acessa — em modo somente-leitura, mais uma ação de sinalização de baixo risco — um recorte curado do que o motor analítico da GD Conecta já produz: indicadores de performance logística, benchmark de mercado, evolução de custo de frete e o plano de ação/recomendações em andamento para a empresa dele.

Três telas compõem esta versão:

1. **Login** — autenticação do usuário-cliente.
2. **Dashboard Executivo** — chegada direta após login (sem menus intermediários): resumo executivo em formato semáforo, 5 indicadores-chave, 4 visualizações, e a tabela de plano de ação.
3. **Oportunidades Prioritárias** — lista das iniciativas de maior impacto financeiro, acessível a partir de um botão de destaque no Dashboard, com a única ação de escrita desta versão ("priorizar").

## 2. Problema de negócio

Hoje o cliente da GD Conecta recebe indicadores, benchmark e plano de ação apenas por e-mail, apresentação pontual ou reunião com o analista — nunca de forma contínua e sob demanda. Isso tem custo dos dois lados: para o cliente, a sensação de acompanhamento é intermitente; para o analista, parte do tempo é gasto respondendo perguntas de status que o próprio cliente poderia autoatender, sem que isso exija nenhum trabalho analítico novo (o dado já existe, só não é acessível diretamente). Ver `v6.18.0_validacao_estrategica.md` §2.1 e §2.2 para a análise completa de alinhamento estratégico, incluindo o tratamento explícito da tensão entre esta funcionalidade e a priorização histórica "Analista primeiro".

## 3. Objetivos da versão

| # | Objetivo | Métrica de sucesso |
|---|---|---|
| OBJ-1 | Dar ao cliente acesso contínuo, sob demanda, a um recorte do que já é calculado hoje pelo motor analítico | Login funcional, escopado por `empresa_id`, sem depender de e-mail/reunião para o cliente ver o próprio status |
| OBJ-2 | Não introduzir nenhum cálculo, indicador ou fórmula nova | 100% dos números exibidos no Portal são lidos de use cases/endpoints já existentes para o analista (`score_logistico.py`, `benchmark.py`, `recomendacoes.py`) — nenhuma query paralela |
| OBJ-3 | Reduzir a interrupção do analista para perguntas de status já respondíveis pelo próprio dado | Indireto — não mensurável nesta versão (sem instrumentação de "perguntas evitadas"); tratado como hipótese de produto, não como critério de aceite obrigatório |
| OBJ-4 | Manter o escopo estritamente somente-leitura, salvo uma única ação de baixo risco | Nenhum endpoint do Portal grava em tabela do motor analítico (CT-e, benchmark, indicador); a única escrita é a marcação de "priorizada" numa oportunidade, sem efeito sobre o cálculo |
| OBJ-5 | Isolar completamente a autenticação e o escopo de dado do cliente da autenticação interna dos analistas | Token de sessão do Portal nunca aceito por endpoint interno e vice-versa; usuário-cliente nunca herda papel de RBAC interno (`VISUALIZADOR`, `ADMIN`, etc. — ver achado SEC-01, `11_changelog.md` [6.9.1]) |

## 4. Dependência de dados

| Dado necessário | Disponível hoje? | Fonte real (a confirmar na Especificação Técnica) |
|---|---|---|
| Performance logística (score) | ✅ Sim | `app/application/use_cases/score_logistico.py` |
| Benchmark de mercado, inclusive comparativo por cliente | ✅ Sim | `app/application/use_cases/benchmark.py`, `benchmark_dashboard.py` (`_comparativo_por_cliente`) |
| Recomendações / plano de ação | ✅ Sim | `app/application/use_cases/recomendacoes.py` |
| Evolução mensal de custo de frete | ✅ Sim (já usado no Dashboard Executivo do analista) | A confirmar endpoint exato na Especificação Técnica |
| Custo por região (UF) | ⚠️ A confirmar | A plataforma já segmenta por região no Benchmark Regional — a granularidade exata (UF vs. macrorregião) precisa ser confirmada contra o código real |
| Autenticação de usuário-cliente | ❌ Não existe hoje | Único item genuinamente novo desta versão — hoje só existe autenticação interna (JWT/cookie httpOnly, `app/core/security.py`, RBAC por `perfil`) |
| Vínculo usuário-cliente ↔ empresa | ❌ Não existe hoje | A definir na Especificação Técnica — provavelmente uma tabela nova de usuários-cliente com FK para `EmpresaModel`, nunca reaproveitando a tabela de usuários internos |
| "Priorizar oportunidade" (estado de sinalização) | ❌ Não existe hoje | Requer um campo/tabela novo, pequeno, desacoplado do motor analítico (não altera nenhum cálculo) |

**Nota importante, análoga à §4.2 da v6.7.0**: assim como aquela versão foi rigorosa sobre não afirmar "pedido fragmentado" sem dado que sustentasse, este PRD é rigoroso sobre não afirmar que qualquer indicador do Portal é "novo" — todos, exceto a autenticação de cliente e o estado de "priorizada", devem ser leituras diretas do que já existe. Se a Especificação Técnica encontrar um indicador do protótipo (§5) que não tem fonte real equivalente hoje, a funcionalidade correspondente deve ser cortada ou adiada — nunca implementada como cálculo novo só para preencher a tela.

## 5. Escopo funcional

### 5.1 Tela 1 — Login

Autenticação de e-mail/senha, própria do Portal (não reaproveita login interno). Mesmos elementos já validados no protótipo (§ver companion): opção "manter conectado", recuperação de senha (pode ficar como funcionalidade futura, não bloqueadora desta versão), redirecionamento direto ao Dashboard Executivo após autenticação — sem tela de menu intermediária.

### 5.2 Tela 2 — Dashboard Executivo

| Bloco | Conteúdo | Fonte (a confirmar na Especificação Técnica) |
|---|---|---|
| Resumo executivo (semáforo) | 4 linhas de status (Performance Logística, Benchmark Mercado, Economia Potencial, Plano de Ação), cada uma com indicador verde/amarelo/vermelho | Derivado dos mesmos 5 KPIs abaixo, com regra de corte simples (ex.: performance ≥ 70 = verde) |
| Botão de destaque | "Ver oportunidades prioritárias" → leva à Tela 3 | — |
| 5 KPIs | Economia Potencial (R$), Aderência ao Mercado (%), Performance Logística (pontos), Rotas acima do benchmark (contagem), Transportadoras Monitoradas (contagem) | `score_logistico.py`, `benchmark.py` |
| Evolução do Frete | Série mensal, custo real vs. referência de mercado | Fonte já usada no Dashboard Executivo do analista |
| Benchmark Mercado | Comparação por categoria de custo (empresa vs. mercado) | `benchmark.py` |
| Custo por Região | Custo médio por UF/região | A confirmar granularidade real |
| Potencial de Economia | Total + composição por categoria de oportunidade | `recomendacoes.py` (ou equivalente de potencial de economia, já existente desde `11_changelog.md` [1.4.0]) |
| Plano de Ação | Lista de ações com status (pendente/andamento/concluído) | `recomendacoes.py` |

### 5.3 Tela 3 — Oportunidades Prioritárias

Lista das oportunidades de maior impacto financeiro (derivadas do mesmo Potencial de Economia da Tela 2), ordenadas por valor, cada uma com:
- Título, descrição curta, categoria, prioridade, status.
- Valor de impacto anual estimado.
- Ação **"Priorizar"** — único ponto de escrita desta versão: marca a oportunidade como sinalizada pelo cliente. Não altera nenhum dado do motor analítico, não recalcula nada — é metadado de interesse do cliente, consumível futuramente pelo analista (fora de escopo desta versão notificar o analista automaticamente — ver §6).

### 5.4 Menu / navegação

Menu lateral reduzido a 7 itens: Dashboard Executivo (ativo), Diagnóstico, Benchmark, Inteligência, Governança, Relatórios, Minha Conta. Apenas Dashboard Executivo e Oportunidades Prioritárias são funcionais nesta versão — os demais itens exibem aviso "ainda não disponível" (nenhuma navegação quebrada, nenhuma promessa de funcionalidade não entregue).

## 6. Fora de escopo (explícito)

| Item | Status | Motivo |
|---|---|---|
| Telas próprias de Diagnóstico, Benchmark, Inteligência, Governança, Relatórios, Minha Conta | ❌ OUT | Ficam para versões futuras, após validação deste primeiro recorte |
| Qualquer escrita que altere dado do motor analítico | ❌ OUT | O Portal é somente-leitura, exceto "priorizar" (metadado desacoplado) |
| Notificação automática ao analista quando o cliente "prioriza" uma oportunidade | ❌ OUT | Integração futura — nesta versão, o estado fica só registrado, consultável manualmente |
| Múltiplas empresas por login de cliente | ❌ OUT | Um usuário-cliente pertence a uma única empresa nesta versão |
| Onboarding self-service (cliente se cadastra sozinho) | ❌ OUT | Cadastro de usuário-cliente é manual pela equipe GD Conecta nesta versão |
| Exportação/relatório do Portal (PDF, Excel) | ❌ OUT | O Relatório Executivo HTML já existente continua sendo o artefato de exportação oficial (`22_plano_diretor_tecnico.md` §18) |
| Qualquer decisão de arquitetura, endpoint, schema, migration ou implementação de código | ❌ OUT desta rodada | Pertence à Especificação Técnica, etapa seguinte, ainda não iniciada |

## 7. Critérios de aceite (para a etapa de implementação futura — não avaliáveis nesta rodada, listados para orientar a Especificação Técnica)

| # | Critério |
|---|---|
| CA-1 | Login do Portal usa autenticação própria, nunca aceita nem é aceito por token de sessão interno (analista) |
| CA-2 | Usuário-cliente nunca herda papel de RBAC interno (`VISUALIZADOR`, `ADMIN`, etc.) |
| CA-3 | Todo indicador exibido no Dashboard Executivo do Portal é lido de um use case/endpoint já existente para o analista — nenhuma query duplicada |
| CA-4 | O isolamento por `empresa_id` é respeitado em toda leitura do Portal — um usuário-cliente nunca vê dado de outra empresa |
| CA-5 | A ação "priorizar" não altera nenhuma tabela do motor analítico (CT-e, benchmark, indicador, recomendação) |
| CA-6 | Os 6 itens de menu não implementados exibem aviso claro, sem navegação quebrada ou promessa de conteúdo inexistente |
| CA-7 | Nenhuma implementação desta versão introduz tabela, use case ou tela paralela para um cálculo que já existe no motor analítico |
