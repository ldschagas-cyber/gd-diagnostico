## 0. Resumo executivo (para quem só vai ler uma seção)

O Portal do Cliente é um **app novo, separado do painel do analista**, com **autenticação própria** (cookies httpOnly distintos, claim de audiência dedicada) e **isolamento de empresa não-manipulável** (o `empresa_id` nunca vem de path/query do cliente — vem só do token). O backend ganha:

- 1 entidade de domínio nova (`ClientePortalUser`), 1 tabela de usuário-cliente, 1 tabela pequena e desacoplada para o estado "priorizada pelo cliente".
- 1 router novo (`/api/v1/portal/*`), reaproveitando **sem exceção** os use cases que já existem para o analista — nenhum cálculo novo, nenhuma tabela analítica nova.

Duas lacunas de dado reais foram encontradas ao verificar o código (não existiam na documentação nem no protótipo) e exigem **ajuste de escopo antes da implementação** (detalhado em §3.8):

1. **"Custo por Região" no protótipo mostra UF (SP, MG, PR...) — mas a plataforma só agrega por macrorregião (Norte/Nordeste/Centro-Oeste/Sudeste/Sul) hoje.** Ajuste: o card vira "Custo por Macrorregião", 5 itens, dado real.
2. **"Valor de impacto anual" por oportunidade individual não existe** — só existe anualização agregada (`PotencialEconomia.proj_anual`, uma economia anual só, não por item). Ajuste: o rótulo da UI deve dizer "impacto estimado no período analisado", não "anual", até (se algum dia for priorizado) uma normalização por item ser implementada.

Nenhuma outra parte do protótipo exigiu ajuste — os 5 KPIs, os demais 3 gráficos, e o Plano de Ação/Oportunidades (via `RecomendacaoModel`, que já tem `status` e `economia_estimada`) têm fonte real confirmada.

O frontend do Portal é um **app React novo** (não reaproveita o `AppLayout`/menu do painel interno) — a investigação confirmou que a aplicação atual não tem nenhum mecanismo de "modo restrito" para diferenciar usuário interno de usuário-cliente, então separar é a única opção sem gambiarra.

### 3.2 Infraestrutura — model e repositório

`app/infrastructure/database/models/__init__.py` (acrescentar):

```python
class ClientePortalUserModel(Base):
    __tablename__ = "clientes_portal_users"
    id: Mapped[int] = mapped_column(Integer, primary_key=True)
    empresa_id: Mapped[int] = mapped_column(ForeignKey("empresas.id"), nullable=False, index=True)
    nome: Mapped[str] = mapped_column(String(200))
    email: Mapped[str] = mapped_column(String(200), unique=True, index=True)
    hashed_password: Mapped[str] = mapped_column(String(255))
    ativo: Mapped[bool] = mapped_column(Boolean, default=True)
    ultimo_acesso: Mapped[datetime | None] = mapped_column(DateTime, nullable=True)
    created_at: Mapped[datetime] = mapped_column(DateTime, server_default=func.now())
```

`ClientePortalUserRepository` em `app/infrastructure/database/repositories/__init__.py`, mesmo padrão de `UserRepository` (implementa a interface acima + `mappers.py::cliente_portal_user_to_domain`).

**E-mail globalmente único** (`unique=True` na coluna) — decisão deliberada: o login não pergunta "de qual empresa" antes de autenticar, então o e-mail precisa ser único no sistema todo (diferente de `UserModel.email`, que também é único hoje, mas por motivo distinto — usuário interno é 1 pessoa só, já o cliente-portal poderia em tese repetir e-mail entre empresas diferentes se não fosse essa regra; optamos por não permitir, para manter o login simples).

### 3.3 Autenticação — cookies e claim dedicados

Reaproveita `create_access_token`/`decode_access_token`/`CryptContext` de `app/core/security.py` (mesmo hashing, mesmo `SECRET_KEY`/`ALGORITHM`), mas com:

- **Cookies com nomes distintos**: `gd_frete_cliente_access` / `gd_frete_cliente_refresh` (nunca `gd_frete_access`/`gd_frete_refresh`, que são do painel interno) — evita colisão de sessão no mesmo navegador se algum dia os dois apps forem acessados na mesma origem.
- **Claim de audiência obrigatória**: `payload["aud"] = "portal_cliente"` em todo token emitido pro Portal (o payload de token interno não tem essa claim hoje — ausência de claim = token interno).
- **Ajuste defensivo em `get_current_user`** (dependency do painel interno, `app/presentation/api/dependencies.py`): adicionar checagem explícita `if payload.get("aud") == "portal_cliente": raise credentials_exception` — garante que um token de cliente nunca é aceito por engano numa rota interna, mesmo que o cookie/header vaze entre os dois apps. Esta é a única alteração num arquivo/comportamento existente prevista nesta especificação — é aditiva (uma checagem a mais) e não muda o comportamento de nenhum token interno válido.
- `REFRESH_COOKIE_PATH` do Portal: `f"{settings.API_V1_PREFIX}/portal/auth"` (mesmo padrão de escopo restrito já usado para o refresh interno).

### 3.4 Dependency de autorização — `get_current_cliente_user`

Nova função em `app/presentation/api/dependencies.py`, espelhando `get_current_user`, mas:

```python
def get_current_cliente_user(
    request: Request,
    cliente_repo: IClientePortalUserRepository = Depends(get_cliente_portal_user_repo),
) -> ClientePortalUser:
    token = request.cookies.get(CLIENTE_ACCESS_COOKIE_NAME)
    if not token:
        raise credentials_exception
    payload = decode_access_token(token)
    if payload.get("aud") != "portal_cliente" or payload.get("type") != "access":
        raise credentials_exception
    user = cliente_repo.get(int(payload["sub"]))
    if not user or not user.ativo:
        raise credentials_exception
    return user
```

**Diferença deliberada do padrão interno**: não existe `verificar_acesso_empresa(empresa_id: int, ...)` lendo `empresa_id` de path — nenhuma rota do Portal recebe `empresa_id` como parâmetro vindo do cliente. Todo endpoint do Portal usa `current_user.empresa_id` diretamente (o cliente nunca pode pedir o dado de outra empresa trocando um número na URL, porque não há número pra trocar).

### 3.8 Lacunas de dado — ajustes de escopo obrigatórios antes da implementação

1. **"Custo por Região" → "Custo por Macrorregião"**: o protótipo (`v6.18.0_wireframe_portal_executivo_dashboard.html`) mostra barras por UF (SP, MG, PR, RJ, SC, BA) com valores ilustrativos. **Isso não existe na plataforma** — todo agregado geográfico do motor é por macrorregião (`NORTE/NORDESTE/CENTRO_OESTE/SUDESTE/SUL`), nunca por UF, em nenhum use case de dashboard/benchmark (confirmado por leitura de `benchmark.py`). Correção obrigatória de escopo: o card mostra as 5 macrorregiões, não UFs. Isso deve ser refletido no protótipo (ajuste de conteúdo, não de arquitetura de tela) antes ou durante a implementação do frontend do Portal.
2. **"Impacto anual" por oportunidade individual**: `RecomendacaoModel.economia_estimada` é o valor calculado sobre o **período de dados analisado**, sem normalização/anualização — diferente de `PotencialEconomia.proj_anual`, que é uma projeção anual, mas só **agregada** (uma economia anual total da empresa, não por item). Não existe hoje um "impacto anual" calculado por oportunidade individual. Correção obrigatória: o rótulo na tela de Oportunidades Prioritárias deve dizer **"impacto estimado no período analisado"**, não "por ano" — mesma disciplina que a v6.7.0 aplicou à terminologia de fragmentação (nunca afirmar o que o dado não sustenta). Se uma normalização por item for desejada no futuro, é uma funcionalidade nova, com sua própria validação, fora desta versão.

Nenhuma outra parte do protótipo exigiu ajuste contra o código real.

## 5. Frontend

**Decisão**: app novo `frontend-portal/` (Vite + React), **não** uma rota dentro do `frontend/` atual — confirmado pela investigação que a aplicação hoje não tem nenhum mecanismo de "modo restrito"/guard por tipo de usuário (só admin/não-admin), então reaproveitar o app existente exigiria construir esse mecanismo do zero mesmo assim, sem ganho real sobre um app separado.

- **Stack**: React 18 + Vite + React Router + React Query (mesmas versões do `frontend/`, por consistência de manutenção) — mas **sem MUI/Recharts**: a identidade visual do Portal já foi definida e aprovada nos wireframes HTML (paleta Índigo/Âmbar/Azul/Marfim, IBM Plex), estilo "plataforma executiva", deliberadamente distinto do painel operacional MUI do analista. Gráficos como SVG à mão (idêntico ao já usado nos wireframes aprovados) ou uma lib leve equivalente — decisão de implementação, não bloqueia esta especificação.
- **Autenticação**: `AuthContext` análogo ao `frontend/src/contexts/AuthContext.jsx`, mas contra `/api/v1/portal/auth/*`; cliente axios com `withCredentials: true` (mesmo padrão), sem `EmpresaContext` (o cliente-portal tem exatamente 1 empresa, fixa no token — não há seleção).
- **Roteamento**: `/login` público; `/` (Dashboard Executivo) e `/oportunidades` protegidas por um `ProtectedRoute` simplificado (sem a lógica de `precisaEscolherEmpresa`, que não existe para o Portal).
- **Páginas**: recriação em React dos 3 wireframes já aprovados (`v6.18.0_wireframe_portal_executivo_{login,dashboard,oportunidades}.html`), com dado mock substituído pelas chamadas reais aos endpoints de `§3.5`.

## 6. Performance

Nenhum endpoint novo introduz agregação pesada nova — todos delegam a use cases já em produção, com o mesmo perfil de custo que já atendem o Dashboard Executivo do analista hoje. Único ponto de atenção: `GET /portal/dashboard` faz várias chamadas de use case em sequência (score, benchmark, recomendações) — implementar em paralelo (ou um único agregador no backend, como `dashboard_executivo()` já faz para benchmark) para não somar latências desnecessariamente. Sem requisito de paginação nesta versão (volumes pequenos: 1 empresa por requisição, poucas dezenas de recomendações).

## 7. Segurança

- Cookies httpOnly, `secure` em produção, `samesite=lax` — mesmo padrão já testado (`test_cookie_auth_v6_5_1.py`) e mitigação já aprovada (S-04).
- Claim `aud="portal_cliente"` obrigatória e verificada nos dois sentidos (§3.3) — mitiga o risco já identificado na Validação Estratégica (§2.6.2) de confusão entre RBAC interno e acesso de cliente.
- Rate limiting no login do Portal, mesmo padrão de 10/min já aplicado ao login interno (slowapi).
- CORS: `frontend-portal/` roda em origem própria — precisa ser adicionada a `settings.BACKEND_CORS_ORIGINS` (config, não código) quando o domínio/porta de dev for definido.
- Isolamento: nenhuma rota do Portal aceita `empresa_id` de fora do token (§3.4) — elimina por construção a classe de vulnerabilidade "trocar o id na URL" que existe, mitigada por autorização, no padrão interno.

## 10. Estratégia de implementação (incremental)

1. Migration das 2 tabelas novas + seed de 1 usuário-cliente piloto (empresa real já cadastrada).
2. Autenticação do Portal (cookies, claim, dependency) + ajuste defensivo em `get_current_user`.
3. `GET /portal/dashboard` e `GET /portal/oportunidades` (leitura, reaproveitando use cases).
4. `PATCH /portal/oportunidades/{id}/priorizar`.
5. `frontend-portal/` — Login, depois Dashboard, depois Oportunidades, ligados aos endpoints acima.
6. Testes (§8) a cada etapa, não só ao final.
