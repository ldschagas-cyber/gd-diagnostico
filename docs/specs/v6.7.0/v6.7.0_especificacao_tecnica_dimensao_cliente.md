### 3.1 `_agregar_clientes()` — inalterado na Revisão 2 quanto à agregação financeira

A estrutura descrita na Revisão 1 (reaproveitar `_norm_nome`/`_raiz` de `_agregar_transportadoras`, extraídas para nível de módulo) permanece válida sem mudança. O que esta revisão adiciona é **um passo extra dentro do mesmo método**: somar `composicao_frete` de cada `CTeModel` do lote, por categoria, junto com `frete`/`peso`/`merc`:

```python
def _agregar_clientes(
    self, empresa_id, periodo, ctes, ref_rs_kg,
) -> List[DlgAnaliticoModel]:
    grupos: Dict[..., List[CTeModel]] = defaultdict(list)
    for c in ctes:
        grupos[_ident_cliente(c)].append(c)

    rows = []
    for ident, lote in grupos.items():
        frete = sum(c.valor_frete or 0 for c in lote)
        peso  = sum(c.peso or 0 for c in lote)
        merc  = sum(c.valor_mercadoria or 0 for c in lote)
        # ── composição agregada (Revisão 2) ──────────────────────────
        comp_agregada: Dict[str, float] = defaultdict(float)
        for c in lote:
            for categoria, valor in (c.composicao_frete or {}).items():
                comp_agregada[categoria] += valor
        ...
        rows.append(DlgAnaliticoModel(
            ..., composicao_frete=dict(comp_agregada),
        ))
    return rows
```

Custo adicional: O(total de CT-e do período), mesmo já percorrido para somar frete/peso/merc — não é uma passada extra sobre o banco, é mais trabalho por CT-e já em memória (ver §6).

#### 3.1.1 RN-68 — Deduplicação de identidade do cliente (algoritmo, Revisão 3)

A Revisão 1/2 já declarava a intenção ("reaproveitar `_norm_nome`/`_raiz` de `_agregar_transportadoras`, extraídas para nível de módulo") sem detalhar o algoritmo. Verificação contra `dlg.py:373-441` (RN-28, `_agregar_transportadoras`) confirma que existe hoje um padrão de identidade exatamente análogo, em produção, que a RN-68 deve replicar — a única função que **não existe ainda** é `_ident_cliente` (precisa ser criada):

```python
# dlg.py — hoje, dentro de _agregar_transportadoras (RN-28):
_SUFIXOS = (" ltda", " me", " epp", " eireli", " sa", " s a")

def _norm_nome(s: str) -> str:
    s = (s or "").strip().lower()
    s = "".join(c for c in unicodedata.normalize("NFKD", s) if not unicodedata.combining(c))
    s = re.sub(r"[^\w\s]", " ", s, flags=re.UNICODE)
    s = " ".join(s.split())
    mudou = True
    while mudou:
        mudou = False
        for suf in _SUFIXOS:
            if s.endswith(suf):
                s = s[: -len(suf)].strip()
                mudou = True
    return s

def _raiz(cnpj: str) -> str:
    return cnpj[:8] if cnpj and len(cnpj) >= 8 else cnpj

# NOVO — RN-68, análogo a _ident (linha 425-430) mas lendo do próprio CTeModel,
# não de um dict de cadastro (destinatário não tem tabela mestre nesta versão):
def _ident_cliente(c: CTeModel) -> tuple:
    cnpj = _so_digitos(c.destinatario_cnpj or "")
    if cnpj:
        return ("RAIZ", _raiz(cnpj))
    nome = _norm_nome(c.destinatario_nome or "")
    return ("NOME", nome) if nome else ("SEM_ID", None)
```

**Diferenças deliberadas em relação a RN-28** (`_ident` original agrupa por `id` de cadastro de transportadora; aqui não há cadastro):
1. Não existe canonicalização "global por competência" (RN-28 passo 3) — não há um "id de cliente" persistido para estabilizar entre meses, porque não existe tabela mestre de cliente nesta versão (decisão já tomada em §2, item 3). A `chave` da linha `dlg_analitico` para Cliente é a própria tupla de identidade (`RAIZ:xxxxxxxx` ou `NOME:...`) serializada como string, não um id inteiro — suficiente porque nenhum consumidor externo (como `mcl._perf_dlg` faz com transportadora) referencia "cliente" hoje.
2. `("SEM_ID", None)` mapeia para o rótulo **"Cliente não identificado"** (PRD CA-2) — grupo próprio, nunca descartado nem fundido com outro cliente sem CNPJ/nome.
3. `_so_digitos` (normalização de CNPJ) já existe e é reaproveitada de `repositories/__init__.py:164-173` — nenhuma função nova de normalização de CNPJ é necessária, só a leitura do campo novo `destinatario_cnpj`.

**RN-68 (texto final para `docs/06_regras_de_negocio.md`, a inserir na Etapa 8/documentação)**: *"Deduplicação de cliente por identidade real: raiz de 8 dígitos do `destinatario_cnpj`, ou nome normalizado (minúsculas, sem acentos/pontuação, sem sufixos societários LTDA/ME/EPP/EIRELI/SA) quando não há CNPJ; CT-e sem nenhum dos dois é agrupado sob 'Cliente não identificado', nunca omitido ou fundido incorretamente — mesmo padrão de identidade já usado pela RN-28 (transportadoras), adaptado para ler diretamente de `CTeModel` em vez de uma tabela de cadastro."*

### 3.2 Frete Transporte Principal / Componentes Adicionais (RN-72)

Calculado a partir de `comp_agregada` (§3.1), **sem query adicional**:

```python
frete_principal = comp_agregada.get("Frete Peso", 0.0) + comp_agregada.get("Frete Valor", 0.0)
adicionais_rs   = max(0.0, frete - frete_principal)
adicionais_pct  = _div(adicionais_rs, frete) * 100
```

Nota: `frete_principal` pode ser menor que `frete` mesmo quando `comp_agregada` está vazio (CT-e sem `Comp` detalhado no XML, ou Excel sem composição) — nesse caso `adicionais_rs` seria calculado incorretamente como igual a `frete` inteiro (falso positivo de "100% adicionais"). **Tratamento obrigatório**: quando `comp_agregada` está vazio para o lote inteiro, `pct_componentes_adicionais` deve ser `None`/omitido (não zero, não 100%) — sinalizando "sem dado de composição", não "sem adicionais". Isso é análogo ao tratamento de `SEM_REF` já usado para benchmark (RN-25) — reaproveitar a mesma filosofia de "ausência de dado é um estado próprio, não um zero".

### 3.4 Sinal de fragmentação operacional (RN-75)

Diferente de §3.2/§3.3 (derivável só da linha do próprio cliente), a fragmentação exige **dois níveis de comparação**, com custos diferentes — decisão de onde calcular cada parte é a parte não-trivial desta seção:

**Parte A — peso médio baixo relativo aos outros clientes** (barata: já temos todas as linhas `CLIENTE_FINAL` do período em memória dentro de `_processar_periodo`):
```python
pesos_medios = [r.peso_total / r.qtd_ctes for r in linhas_cliente if r.qtd_ctes]
mediana_peso_medio = statistics.median(pesos_medios) if pesos_medios else 0
# por linha:
peso_medio_baixo = row.peso_total / row.qtd_ctes < mediana_peso_medio * LIMIAR  # ex. 0.5
```
Calculado uma vez por período, depois de todas as linhas de `CLIENTE_FINAL` estarem agregadas — uma passada O(n) sobre o número de clientes distintos (não sobre CT-e), portanto barata mesmo com milhares de clientes.

**Parte B — frequência de despacho em janela curta** (mais cara: exige as *datas individuais* de cada CT-e do cliente, que **não estão** em `dlg_analitico` — só em `ctes`):
```python
# só roda para clientes já sinalizados por Parte A E classificados ATENÇÃO/CRÍTICO —
# não para todos os clientes, ver justificativa de custo abaixo
datas = sorted(c.data_emissao for c in ctes_do_cliente_no_periodo)
despacho_frequente = _tem_janela_curta(datas, min_ctes=3, dias=7)  # RN-75
```

**Decisão de custo**: Parte B só é executada para o **subconjunto** de clientes que já passaram por Parte A **e** estão classificados ATENÇÃO/CRÍTICO (RN-25) — não para todos os clientes do período. Justificativa: fragmentação só é uma causa candidata quando já existe desvio de custo a explicar (RN-76, passo 1); calcular Parte B para clientes EFICIENTE seria trabalho sem uso. Como os CT-e do período já estão carregados em memória (`_carregar_ctes`, usado por todas as agregações), Parte B não é uma nova query — é um `groupby` adicional sobre a mesma lista já carregada, filtrado ao subconjunto de identidades de cliente que precisam da checagem.

Mesma classe de limitação já assumida para o campo de destinatário (§4.1) — deve ser comunicada com a mesma transparência (nota de UI, não silêncio).

#### 3.5.1 Reprocessamento — o que `POST /processar` faz e não faz (achado da Revisão 3)

Este é o ponto de maior risco de mal-entendido do PRD/spec e foi verificado diretamente contra o código:

- **`POST /dlg/{empresa_id}/processar`** (`dlg.py` router, use case `dlg.py:79-119`) carrega `CTeModel` já persistidos (`_carregar_ctes`) e **recria** `DlgAnaliticoModel`/`DlgOutlierModel` do período — é idempotente e correto para recalcular agregações a partir do dado que já está no `CTeModel`. É exatamente o mecanismo usado na v6.6.0 (CONS-01) para propagar a correção de RN-09 sem reimportar nada.
- **Isso não serve para esta versão da mesma forma**: `destinatario_cnpj`, `destinatario_nome` e a categorização de `composicao_frete` **são campos do próprio `CTeModel`, escritos uma única vez, no momento do parse do XML/Excel na importação**. `processar()` não volta a tocar no XML — ele só lê o que já está gravado. Rodar `processar()` em CT-e antigos recalcula `dlg_analitico.composicao_frete` (a soma agregada, RN-72) **a partir do valor antigo** já persistido em `CTeModel.composicao_frete` — ou seja, "Outros" continua contendo TDE/TDA/Estadia não discriminados, porque a fonte não mudou.
- **Reimportar o XML original não resolve, e é ativamente bloqueado**: a deduplicação por chave de acesso (RN-02, `importacao.py:76-78`) descarta como duplicado qualquer CT-e cuja chave já exista no banco — `self.cte_repo.get_by_chave(parsed.chave)` — o registro existente **não é atualizado**, o arquivo simplesmente é contado em `resultado.duplicados` e ignorado. Reenviar o mesmo XML depois do deploy da v6.7.0 não populará `destinatario_*` nem recategorizará `composicao_frete` do CT-e já existente.
- **Conclusão**: não existe hoje nenhum caminho — nem `processar()`, nem reimportação — que corrija dado histórico. As únicas opções reais, ambas fora de escopo desta versão, seriam: (a) um script de backfill dedicado que localize por chave e faça `UPDATE` explícito em vez de passar pelo fluxo de dedup de importação, ou (b) apagar e reimportar os CT-e afetados (destrutivo, não recomendado sem necessidade forte). **Decisão de produto**: aceitar a limitação como permanente para o dado pré-v6.7.0, documentá-la com transparência (CA-12), e não implementar nenhum backfill "de brinde" durante esta versão — registrar como item de backlog técnico separado se a necessidade surgir.

**Novo método**, determinístico, em `dlg.py`:

```python
def _diagnosticar_causa(
    self, row: DlgAnaliticoModel, limiar_adicionais_pct: float, tem_fragmentacao: bool,
) -> Dict:
    """RN-76: atribui causa dominante ao desvio de um cliente ATENÇÃO/CRÍTICO.
    Retorna {"causa": "ADICIONAIS"|"FRAGMENTACAO"|"AMBAS"|"NENHUMA", "detalhe": {...}}.
    Só é chamado para linhas com classificacao in (ATENCAO, CRITICO) — RN-25.
    """
    tem_adicionais = (row.pct_componentes_adicionais or 0) > limiar_adicionais_pct
    if tem_adicionais and tem_fragmentacao:
        causa = "AMBAS"
    elif tem_adicionais:
        causa = "ADICIONAIS"
    elif tem_fragmentacao:
        causa = "FRAGMENTACAO"
    else:
        causa = "NENHUMA"
    return {"causa": causa, "componente_top": row.ranking_componentes[0] if tem_adicionais else None}
```

`limiar_adicionais_pct` = referência configurável (recomendação inicial: mediana de `pct_componentes_adicionais` entre todos os clientes da empresa no período — mesma filosofia de threshold relativo já usada em outras regras da plataforma, ex. RN-49/52, em vez de um valor fixo arbitrário). Deve ser calculável a partir das linhas já agregadas de `CLIENTE_FINAL`, sem query adicional.

#### 3.6.1 Onde expor o resultado

Duas opções, com trade-off explícito:

- **(a) Calcular e persistir em `dlg_analitico` no momento do `processar()`**, junto com `composicao_frete` — vantagem: leitura (`listar`) não recalcula nada; desvantagem: exige que a Parte B da fragmentação (§3.4, que consulta `ctes` por data) rode dentro do fluxo de escrita, aumentando o tempo de `POST /processar`.
- **(b) Calcular sob demanda em `resumo()`/num novo método de leitura**, só para os clientes já retornados como CRÍTICO/ATENÇÃO — vantagem: não onera `processar()`; desvantagem: recalculado a cada leitura (mitigado pelo fato de já ser um subconjunto pequeno, tipicamente top-N clientes críticos).

**Recomendação**: opção (a) para Parte A da fragmentação e para composição/adicionais (baratos, já calculados durante `processar()`), **opção (b) só para Parte B** (janela de despacho, mais cara) — executada sob demanda quando a recomendação (RN-77) ou a ferramenta de IA (`get_ofensor_cliente`, §3.8) precisam do dado, não em toda leitura de tabela. Isso evita pagar o custo de Parte B em cada `GET /analitico` (que pode ser chamado com frequência pela UI), reservando-o para os pontos de consumo que realmente precisam da causa (recomendações e assistente).

### 3.7 Recomendações causais (RN-77, extensão de RN-56/RN-71)

`_recomendacoes_dlg_clientes()` (Revisão 1) passa a chamar `_diagnosticar_causa()` (§3.6) para cada cliente CRÍTICO/ATENÇÃO antes de montar o texto, seguindo os templates do PRD §11. ## 6. Performance — requisito obrigatório (elevado de risco a requisito na Revisão 3)

Delta sobre a Revisão 1 (que já identificou a falta de paginação em `/analitico` como risco principal): a Revisão 3 eleva este item de "risco identificado, não resolvido" para **requisito de aceite obrigatório desta versão (PRD CA-16)** — Cliente é a dimensão com maior cardinalidade potencial das 5 (uma empresa pode ter dezenas de filiais/rotas/transportadoras, mas facilmente centenas ou milhares de clientes destinatários), então o risco que era tolerável nas 4 dimensões existentes deixa de ser tolerável aqui.

- **Composição agregada (§3.1)**: custo marginal pequeno — soma de um dict já carregado por CT-e, mesma ordem de grandeza do resto da agregação.
- **Parte A da fragmentação (§3.4)**: O(número de clientes distintos) por período — barato mesmo em milhares de clientes, porque opera sobre linhas já agregadas, não sobre CT-e.
- **Parte B da fragmentação (§3.4)**: potencialmente o item mais caro desta revisão, mas **deliberadamente restrito** ao subconjunto de clientes CRÍTICO/ATENÇÃO com peso médio baixo — não a todos os clientes. Se, na prática, esse subconjunto ainda for grande (empresa com centenas de clientes críticos), reavaliar se essa parte deve ser assíncrona (ex. calculada sob demanda quando o usuário abre o diagnóstico de um cliente específico, não em lote).
- **Cardinalidade de Cliente continua sendo o maior risco herdado da Revisão 1** — a paginação do endpoint `/analitico` se torna ainda mais relevante nesta revisão, porque cada linha agora carrega mais dado (`composicao_frete` completo, ranking).

**Decisões obrigatórias na Etapa 5 (API), não opcionais** (CA-16):
1. **Paginação** de `GET /analitico?dimensao=CLIENTE_FINAL` — parâmetros `page`/`page_size` (ou `limit`/`offset`), com ordenação server-side pelos critérios do PRD §8 aplicada antes da paginação, não depois.
2. **Filtros server-side** mínimos: por classificação (CRÍTICO/ATENÇÃO/EFICIENTE) e por período — evita que o frontend precise baixar a listagem inteira para filtrar localmente.
3. **Payload por linha medido antes do release**: como `composicao_frete`/`ranking_componentes` são novos e aumentam o tamanho de cada linha, medir o tamanho médio de resposta com uma empresa de referência (maior volume de clientes disponível em ambiente de teste) e confirmar que o tempo de resposta fica dentro do aceitável definido pelo time antes de liberar a dimensão Cliente com dado real.
4. Este trabalho **não é exclusivo de Cliente** — se implementado de forma genérica no endpoint `/analitico`, beneficia as 4 dimensões existentes também (nenhuma regressão, só ganho), reforçando a filosofia de reaproveitamento da Opção B (§2).
