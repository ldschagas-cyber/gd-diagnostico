## 1. Visão geral da funcionalidade

O Dashboard é a **tela inicial do sistema** (rota `/`, primeiro item do grupo "Diagnóstico Logístico") e o endpoint mais usado da plataforma (`A-06`/`PF-01`). Ele responde à pergunta mais básica de um analista de logística ao abrir o sistema: **"como está o custo de frete da minha empresa agora, e onde estão os desvios?"**

Diferente do DLG (`DiagnosticoDLG.jsx`, rota `/diagnostico/dlg`), que permite investigar o custo **por dimensão** (Filial, Rota, Transportadora, Região, Cliente) com drill-down e diagnóstico causal, o Dashboard é uma **visão consolidada de abertura** — indicadores nacionais, dois gráficos regionais, ranking de transportadoras e uma lista textual de oportunidades, sem seletor de dimensão nem drill-down. São dois módulos com propósitos diferentes que compartilham a mesma fonte de dado (CT-e) mas não a mesma arquitetura (Dashboard usa `DiagnosticoUseCase`/agregação SQL direta; DLG usa `DlgUseCase`/tabela `dlg_analitico`).

Em julho/2026 a tela passou por um redesenho ("mock 07/2026", ver comentários em `Dashboard.jsx:186,255,339`) que **reduziu visualmente o escopo** de 5 famílias de indicador para 3, sem remover o código das 2 restantes — elas ficaram guardadas atrás de `{false && (...)}`. O resultado é uma tela em produção com comportamento diferente do que o código-fonte sugere à primeira leitura, e sem nenhum documento que registre se essa redução foi definitiva ou temporária. Esse é o problema central que este PRD resolve.

## 2. Problema de negócio

Dois problemas distintos motivam este documento:

1. **Ausência de especificação formal.** O Dashboard existe desde a v1.0.0 (MVP) e acumulou 7+ ciclos de melhoria (`RF011`–`RF015`, "MELHORIA 3" a "MELHORIA 7", redesenho de julho/2026) inteiramente via comentário de código, sem nunca ganhar uma entrada própria em `docs/02_especificacao_funcional.md` além de um parágrafo de 4 linhas. Qualquer pessoa nova no time (ou uma IA) que leia `Dashboard.jsx` hoje não consegue distinguir, sem investigar o histórico de commits, o que é "desligado de propósito" do que é "esquecido".
2. **Débito técnico visível e já catalogado por auditoria (`UX-09`)**: o comentário `{/* Desempenho de prazo (SLA) — fora do mock, desabilitado (apagar depois). */}` (`Dashboard.jsx:449`) é datado, mas "depois" nunca chegou. Isso não é só estética de código — tem custo de produto real: a tela hoje **não mostra nenhum indicador de prazo/OTIF** (RF014, RN-11) nem indicadores regionais tabulares, mesmo o backend já calculando e devolvendo esses dados em toda resposta de `GET /dashboard/{empresa_id}`. O dado é pago (calculado, transmitido) e não é entregue ao usuário.

Sem uma decisão explícita, a plataforma acumula 3 blocos de UI mortos (~180 linhas de `Dashboard.jsx`, ~200 linhas de `GraficosDiagnostico.jsx`) que continuam a ser lidos, mantidos e potencialmente reativados por engano em mudanças futuras — sem que ninguém tenha decidido produto sobre isso.

## 5. Contrato de API

**Endpoint**: `GET /api/v1/dashboard/{empresa_id}`
**Autorização**: `verificar_acesso_empresa` — 404 se a empresa não existe; 403 se o usuário não tem acesso (admin/superusuário acessa qualquer empresa; usuário comum só a sua própria `empresa_id`).
**Query params**: `data_inicio` (date, opcional), `data_fim` (date, opcional) — sem período, considera todo o histórico.

### 5.1 Estrutura da resposta (`DiagnosticoOut`)

```
{
  empresa_id, empresa_nome, periodo_inicio, periodo_fim,
  nacional: { ... },        // §5.2 — consumido integralmente pela tela
  regionais: [ ... ],       // §5.3 — consumido parcialmente (2 de ~7 campos usados nos gráficos ativos)
  transportadoras: [ ... ], // §5.4 — consumido integralmente pela tabela de ranking
  prazos: [ ... ],          // §5.5 — calculado, transmitido, NÃO exibido (bloco desligado, §9)
  composicao_frete: { ... },// §5.6 — calculado, transmitido, NÃO exibido (bloco desligado, §9)
  oportunidades: [ ... ],   // §5.7 — consumido integralmente
  evolucao_frete: [ ... ]   // §5.8 — consumido pela sparkline do card Frete total
}
```

### 5.2 `nacional` (`IndicadorNacionalOut`)

| Campo | Usado na tela hoje? | Observação |
|---|---|---|
| `valor_total_frete`, `frete_rs_kg`, `frete_pct` | ✅ | Cards 2-4 |
| `meta_rs_kg`, `meta_pct`, `desvio_rs_kg`, `desvio_pct` | ✅ | Legenda + selo de desvio dos cards |
| `qtd_ctes` | ✅ | Legenda do card Frete total quando não há sparkline |
| `valor_total_mercadoria`, `peso_total` | ❌ | Calculados, não exibidos (card "Peso total" desligado, §9) |
| `qtd_ctes_emitidos`, `qtd_ctes_ativos`, `qtd_ctes_cancelados`, `pct_cancelados` | ❌ | Calculados (MELHORIAS 3/4), cards correspondentes desligados (§9) |
| `custo_medio_kg` | ❌ | Hoje é sempre idêntico a `frete_rs_kg` (MELHORIA 7); card desligado (§9) |
| `ref_pct_ideal_max`, `ref_pct_mercado_min`, `ref_pct_mercado_max` | ❌ | Referência de mercado (MELHORIA 6); card desligado (§9) |

### 5.3 `regionais[]` (`IndicadorRegionalOut`)

Campos: `macro_regiao`, `frete_total`, `mercadoria_total`, `peso_total`, `frete_rs_kg`, `frete_pct`, `meta_rs_kg`, `meta_pct`, `qtd_ctes`. Hoje só `frete_rs_kg`/`meta_rs_kg` e `frete_pct`/`meta_pct` alimentam os 2 gráficos ativos (§4, itens 5-6); a tabela "Indicadores regionais" que exibiria os demais campos está desligada (§9).

### 5.4 `transportadoras[]` (`IndicadorTransportadoraOut`)

Campos: `transportadora_id`, `nome`, `frete_total`, `mercadoria_total`, `participacao_pct`, `frete_rs_kg`, `frete_pct`, `custo_medio_entrega`, `qtd_ctes`, `peso_transportado`. Todos usados — na tabela de ranking (§4, item 7) e nos 3 gráficos de transportadora desligados (§9).

### 5.5 `prazos[]` (`IndicadorPrazoOut`) — **calculado, não exibido**

Campos: `macro_regiao`, `prazo_medio`, `entregas_no_prazo`, `entregas_atraso`, `sla_pct`, `prazo_meta`. Depende de `data_saida`/`data_entrega` preenchidas no CT-e (RN-11). Consumido apenas pela tabela "Desempenho de prazo (SLA)" desligada (§9).

### 5.6 `composicao_frete` (dict categoria → R$) — **calculado, não exibido**

Soma por categoria (Frete Peso, Pedágio, GRIS, Seguro, Ademe, Despacho, Outros — mesmas categorias do parser de CT-e) sobre CT-es ativos do período; categorias com valor ≤ 0 são removidas. Consumido apenas pelo gráfico de pizza "Composição do frete" desligado (§9).

### 5.7 `oportunidades[]` (array de string)

Consumido integralmente pelo card "Oportunidades identificadas" (§4, item 8). Regras de geração em §6.4.

### 5.8 `evolucao_frete[]` (`EvolucaoFreteOut`)

Campos: `mes` (AAAA-MM), `frete_total`. Sempre **últimos 6 meses fixos**, independente do filtro de período aplicado na tela — é a tendência de gasto, não o recorte analisado. Consumido pela sparkline do card Frete total.

## 6. Regras de negócio

### 6.1 Regras já documentadas (`docs/06_regras_de_negocio.md`)

| RN | Regra | Onde se aplica no Dashboard |
|---|---|---|
| RN-09 | Apenas CT-es `status=ATIVO` entram nos totais financeiros; `pct_cancelados` é calculado à parte, sobre emitidos | `nacional.*`, `regionais[]`, `transportadoras[]`, `composicao_frete`, `evolucao_frete` |
| RN-10 | `frete_rs_kg = valor_frete / peso`; `frete_pct = valor_frete / valor_mercadoria * 100` | Cards nacionais e ambos os gráficos regionais |
| RN-11 | OTIF (prazo) = aderência ao prazo entre `data_saida` e `data_entrega` | `prazos[]` — calculado, hoje não exibido (§9) |
| RN-12 | Macrorregião de destino derivada da UF via `macro_regiao.py` | Agrupamento de `regionais[]` e `prazos[]` |

### 6.2 Regras não numeradas, existentes apenas no código (`diagnostico.py`)

Estas regras nunca ganharam número RN formal — recomenda-se atribuí-los na consolidação (§14, CA-8):

- **Meta nacional**: se `MetaNacional` cadastrada, `desvio_rs_kg = frete_rs_kg − meta.meta_rs_kg` e `desvio_pct = frete_pct − meta.meta_pct_frete`; sem meta cadastrada, os campos de meta/desvio ficam `null` e o `StatCard` correspondente não exibe selo.
- **Referência de mercado** (MELHORIA 6): `ref_pct_mercado_min/max` vêm do menor/maior `frete_pct_min`/`frete_pct_max` entre os benchmarks cadastrados (`benchmark_repo.list()`); falha silenciosamente (não quebra a tela) se o repositório não estiver disponível ou não houver benchmark.
- **Custo médio por kg** (MELHORIA 7): hoje é sempre um alias de `frete_rs_kg` — não há cálculo diferente entre os dois campos apesar de nomes distintos no schema.

### 6.3 Regra de UI (não é regra de backend)

- **Sparkline mínima de 6 pontos**: a tendência de Frete Total só é desenhada com ≥ 6 meses de dado; com menos, a legenda mostra a quantidade de CT-es no período em vez do gráfico (`Dashboard.jsx:131-133`). Isso é puramente uma decisão de UI (evitar ruído visual com poucos pontos) — o backend sempre devolve o array `evolucao_frete`, mesmo com menos de 6 itens.

### 6.4 Oportunidades (`_oportunidades`, `diagnostico.py:322-356`)

Texto gerado, um item por condição atendida, nesta ordem:

1. `desvio_rs_kg > 0` → frete nacional R$/kg acima da meta.
2. `desvio_pct > 0` → % frete sobre mercadoria acima da meta.
3. Para cada região com `meta_rs_kg` cadastrada e `frete_rs_kg` acima dela → um item por região.
4. Para cada região de prazo com `prazo_meta` cadastrada e `prazo_medio` acima dela → um item por região (cita o SLA%).
5. Se a maior transportadora responde por **> 50%** do frete total → alerta de concentração/dependência.
6. Se nenhuma condição disparar → item único: *"Nenhum desvio relevante frente às metas cadastradas."*

Note que o item 4 depende de `prazos[]` — a regra de oportunidade de prazo **continua ativa e pode aparecer no card de Oportunidades hoje**, mesmo com a tabela de SLA desligada na UI (§9). Ou seja, o usuário pode ver o texto *"Região Sul: prazo médio X dias acima da meta..."* sem nunca ver a tabela de onde esse número vem — uma inconsistência de experiência que a §9 endereça.

## 7. Componentes de UI reutilizados

- **`StatCard`** (`frontend/src/components/StatCard.jsx`): card genérico com rótulo, valor, legenda, ícone e selo de desvio (`Chip` âmbar se o desvio for "ruim" pela direção configurada, verde se "bom"; sem selo se `|desvio| < 0.0001` ou se `desvio` for `null`). Reutilizado pelos cards 3 e 4 (§4); o card 2 (Frete total) usa markup próprio no `Dashboard.jsx` por causa da sparkline.
- **`Sparkline`** (função local em `Dashboard.jsx:53-84`): SVG minimalista sem eixo, normalizado ao próprio min/max da série — não é biblioteca de gráfico, é um componente interno de ~30 linhas.
- **`GraficosDiagnostico`** (`frontend/src/components/GraficosDiagnostico.jsx`): usa Recharts; encapsula cada gráfico em um wrapper `Painel` com estado vazio próprio ("Sem dados para o período.").

## 10. Decisão de escopo proposta

Com base na tabela da §9, a proposta deste PRD para fechar o débito de `UX-09` é:

- **Reativar** (3 blocos): CT-es Ativos/Cancelados, Frete/Mercadoria com referência de mercado, Desempenho de prazo (SLA). Todos usam dado já calculado e transmitido pelo backend hoje — custo de implementação é só de frontend (remover `{false &&`, ajustar layout de grid).
- **Remover em definitivo** (4 blocos): Frete dos CT-es Ativos, Custo Médio por Kg, e os 3 gráficos de transportadora redundantes com a tabela de ranking. Reduz `Dashboard.jsx`/`GraficosDiagnostico.jsx` em ~250 linhas combinadas sem perda de informação ao usuário.
- **Manter desligado, decisão confirmada** (1 bloco): card Peso total.
- **Decisão de produto pendente, não técnica** (2 blocos): tabela Indicadores regionais, gráfico Composição do frete — recomenda-se levar essas duas linhas para validação com quem definiu o mock de julho/2026, antes de reativar ou remover.

Esta seção é uma **proposta**, não uma decisão tomada — os critérios de aceite (§14) tratam a validação dela como pré-requisito de fechamento deste PRD.

## 11. Riscos e achados de auditoria relacionados

- **`A-06`/`PF-01`** (`22_plano_diretor_tecnico.md:125`) — `GET /dashboard/{empresa_id}` ainda carrega todos os CT-e em memória para 2 de 5 componentes (prazo e composição de frete, via `listar_prazos`/`list_by_empresa`, §5.5/§5.6) — as demais 3 agregações já são SQL direto (`agregar_nacional`, `agregar_por_regiao`, `agregar_por_transportadora`). Risco direto de timeout com alto volume de CT-e por empresa, classificado como o único achado de risco de falha visível ao usuário. **Relevante para a decisão da §10**: reativar a tabela de SLA (que consome `prazos[]`) não piora esse risco — o cálculo já roda hoje, mesmo sem a tabela ser exibida; o risco de performance é do backend, independente da decisão de UI.
- **`UX-03`** — empty state "Selecione uma empresa" sem CTA direto. Achado já catalogado, não coberto pelas mudanças propostas aqui — fica registrado como fora de escopo (§13), não esquecido.
- **`UX-09`** — origem direta deste PRD (§2).
- **Cobertura de teste** — não há teste automatizado de frontend para `Dashboard.jsx`, `GraficosDiagnostico.jsx` ou `StatCard.jsx` (achado já catalogado em `docs/15_fase2_qualidade_codigo.md`, item Q-10). Qualquer reativação/remoção decidida na §10 deve, no mínimo, não regredir os testes de backend existentes (`test_cons01_propagacao_rn09.py`, que já valida `GET /dashboard/{empresa_id}` contra o benchmark nacional).

## 12. Multiempresa

`empresa_id` é path param obrigatório, validado por `verificar_acesso_empresa`: administradores/superusuários acessam qualquer empresa; usuário comum só a própria. Toda agregação do `DiagnosticoUseCase` é filtrada por `empresa_id` — nenhuma mudança de escopo deste PRD altera esse isolamento.

## 13. Fora de escopo

- Correção do achado `UX-03` (CTA no empty state) — achado independente, não é sobre os blocos desligados.
- Migração de `prazos`/`composicao_frete` para agregação SQL (resolução de `A-06`/`PF-01`) — é item de performance de backend, rastreado separadamente em `10_roadmap.md`; a decisão de reativar a tabela de SLA (§10) não exige essa migração como pré-requisito, só a evidencia com mais urgência.
- Qualquer mudança na Dimensão Cliente do DLG (`v6.7.0`) — módulo distinto, já documentado em PRD próprio.
- Cache (Redis) para o endpoint de Dashboard (`DT-09`, `10_roadmap.md`) — item de infraestrutura, não de escopo funcional da tela.
- Numeração formal de novas RN para as regras hoje só documentadas em código (§6.2) — recomendado, mas a atribuição do número em si é tarefa de execução, não de especificação (ver CA-8).
